# 设计决策记录

这份文档记录 **ContextDock 每个关键选择的"为什么"**，以及**被否决的替代方案**。

写下来不是为了好看——是因为这些决策**互相咬合**：改一个会连带改多个，
其中几处改起来要重灌全量数据。不写清楚，三天后的自己会推翻今天的自己。

---

## 1. 向量维度固定 1024

**决策**：使用硅基流动 `Pro/BAAI/bge-m3`，原生输出 1024 维，**不做任何截断**。

**为什么不能用 4096 维**——这是 pgvector 的源码级硬限制，不是性能建议：

| 类型 | 存储上限 | **索引**上限 |
| --- | --- | --- |
| `vector` | 16000 维 | **2000 维** |
| `halfvec` | 16000 维 | **4000 维** |
| `bit` | 无限制 | 64000 维 |

4096 > 4000，**连 `halfvec` 都建不了索引**（差 96 维）。没有索引意味着向量检索
退化成全表顺序扫描，等于白做。

建索引时会直接报错，无法绕过：

```text
ERROR: column cannot have more than 2000 dimensions for hnsw index  (SQLSTATE 54000)
```

**这条为什么必须一开始就定死**：换维度 = 重建表 + 重建索引 + **重灌全量向量**。
这是整个项目最贵的一次改动。

### 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| Qwen3-Embedding-8B + 截断到 1024 维 | Matryoshka 降维是**有损**的，且多一个易错参数 |
| 4096 维 + `halfvec` 索引 | 4000 < 4096，建不了 |
| 4096 维 + 二值量化（`bit`） | 有损，需要两段式查询（粗排 + 精排），复杂度不划算 |

## 2. 绝对不给 bge-m3 传 `dimensions` 参数

硅基流动的 `dimensions` 参数**仅对 Qwen/Qwen3 系列生效**。
对 bge-m3 传会返回 **400 错误**，不是静默忽略。

```go
// ❌ 会直接 400
Dimensions: openai.Int64(1024),

// ✅ 删掉这行
```

> 这个坑的隐蔽之处：从 Qwen3 换到 bge-m3 时，`1024` 这个数字**碰巧不用改**，
> 但**必须删掉这个参数**。数字对得上会让人以为代码没问题。

## 3. 中文分词用字符级 bigram

**决策**：按书写系统分流——Han / 平假名 / 片假名走 bigram，拉丁字母按词切。

```text
输入:  使用 pgvector 做向量检索
        └┬─┘ └───┬───┘ └────┬────┘
      CJK段    ASCII段    CJK段
输出: [使用]  [pgvector]  [做向, 向量, 量检, 检索]
```

**为什么不用中文分词库**：

| 库 | 问题 |
| --- | --- |
| `gojieba` | 依赖 **cgo + C++**，`CGO_ENABLED=0` 的交叉编译直接失败 |
| `sego` | 最后提交 2021-08，**五年无维护** |
| `gse` | 纯 Go 可用，但引入词典维护成本；`Segmenter` 还**不是 goroutine-safe** |

bigram 的收益：**零依赖、约 20 行、中文"未登录词"问题天然消失**。

**这不是我拍脑袋的方案**——有生产级背书：
bleve 的 CJK 分析器内部就是 unicode tokenizer + rune bigram filter。
RAGFlow 自研的 `token_similarity()` 同样用 bigram 且权重更高（unigram 0.4 / bigram 0.6）。

> ⚠️ **bigram 不是万能方案**。它只适用于 Han / 平假名 / 片假名。
> 泰文、老挝文、高棉文、缅文虽然也没有空格，但字母本身没有语义，
> 必须用词典分词或 LSTM。Lucene 的 `CJKBigramFilter` 明确**跳过**这些文种
> （它们的 token 类型是 `SOUTHEAST_ASIAN`，过滤器原样透传）。
> 本项目第一版**只处理中英混合**。

## 4. `Chunk.Embedding` 打 `json:"-"`

MCP 工具返回搜索结果时，如果向量被序列化：

```text
10 条结果 × 1024 维 = 10240 个浮点数 ≈ 100KB 纯数字
```

而 Agent 拿到这些数字**毫无用处**——它要的只是 `Content`。

**注意 `json:"-"` 是单向的**：任何"序列化成 JSON 再读回"的路径
（本地缓存、调试快照）都会静默丢掉向量，读回来是 `nil`，
与"还没嵌入"无法区分，可能导致**重复调用 Embedding API 产生费用**。

> 结论：向量只能来自 pgvector，不能走 JSON 往返。

## 5. RRF 的 0 号哨兵必须显式防护

`LexicalRank` / `VectorRank` 用 **0 表示「该通道未召回」**。直接代入公式会出错：

```text
1/(60 + 0) = 0.016667   ← "未召回"，却比第一名还高
1/(60 + 1) = 0.016393   ← 真正的第一名
```

**「未召回」拿到比第一名更高的分。** 这个 bug 不报错，只是排序错乱，
排查时会先怀疑分词和模型。

防护做进了 `SearchResult.RRFScore()`，而不是留给调用方写公式——
**漏掉这个判断不会报错，所以不能靠自觉**。

---

## 6. 融合用 RRF，不用加权求和

**决策**：`RRF(d) = Σ 1 / (k + rankᵢ(d))`，`k = 60`。

**为什么不用加权求和**：BM25 分和余弦相似度**不在同一个数量级**——
BM25 可能是 0~20，余弦是 -1~1。加权求和**必须先做归一化**，
而归一化本身就没有标准答案（min-max？z-score？按什么分布？）。

RRF **只用名次，不用分数**，天然绕开整件事。

> **参考对照**：RAGFlow 用的就是 weighted_sum（默认 `"0.7,0.3"`）。
> 注意它的参数名 `vector_similarity_weight` 有误导性——它指的是**向量**的权重，
> 默认 0.3，所以默认是**关键词占 70%**。
>
> 两种方案都能用。选 RRF 的理由是**它不要求两个分数可比**，
> 而这意味着更少的调参和更稳定的行为。

`k=60` 来自 Cormack、Clarke、Büttcher 的 SIGIR 2009 论文
《Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods》。
Elasticsearch 的 `rank_constant` 默认值同样是 60。
实测 k 在 10~100 区间内对 NDCG@10 的影响不到半个点，所以不用调。

## 7. `StableKey()`：RRF 去重不能用 `Chunk.ID`

RRF 要按某个键把两路结果对应起来。最自然的想法是用 `Chunk.ID`——
但**落库之前所有 chunk 的 ID 都是 0**，两个完全不同的片段会被当成同一条合并，
RRF 名次整体错乱，而且**不报任何错**，只是结果变差。

规则：已落库用 ID，未落库退化为 `(DocumentID, Ordinal)`。

**硬约束：M4 的 RRF 只允许用这个键做映射与去重。**

---

## 8. `IndexText()`：被索引文本的唯一来源

BM25 的分词、文档长度、倒排，和向量的语义空间，**必须建立在同一个文本上**。

如果 Embedder 和 BM25 各自拼一次（分隔符不同，或一边忘了拼面包屑），
两路检索搜的就不是同一个文本——召回不可比、RRF 质量下降，**极难排查**。

**硬约束：凡是「拿去 embed 或建索引」的代码路径，都不允许直接读 `c.Content`。**

---

## 9. `MatchedBy()` 是算出来的，不是存出来的

```go
func (r SearchResult) MatchedBy() []Retriever   // 由 Rank 字段计算
```

新手容易顺手加一个 `MatchedBy []Retriever` 字段，但那是**冗余状态**：
它和 `LexicalRank > 0`、`VectorRank > 0` 说的是同一件事，存两份就有不同步的可能。

> **本项目的通用原则：能用已有字段算出来的，就不要存第二份。**

---

## 10. `SearchResult.Score` 的含义随阶段变化

| 阶段 | Score 的含义 | 典型范围 |
| --- | --- | --- |
| 单路检索 | BM25 分 或 余弦相似度 | 0~20 / -1~1 |
| RRF 融合后 | RRF 分 | 0.01~0.03 |

⚠️ **这是一个多刻度字段，绝对不要跨阶段比较或做阈值过滤。**

典型事故：写 `score >= 0.5` 做阈值过滤，在向量阶段（余弦 -1~1）正常，
切到 RRF 阶段（0.01~0.03）会**把所有结果静默过滤光**，
表现为"混合检索突然没有结果"且不报错。

需要比较时，用同阶段的 Score，或者用拆出来的 `LexicalScore` / `VectorScore`
——它们永远是**原始分**，不受融合阶段影响。

## 11. 数据库版本必须 pin ≥ 0.8.6

pgvector 0.8.6 修复了 **CVE-2026-3172**：并行 HNSW 建索引路径的堆缓冲区溢出，
CVSS 8.1，可读取其他 relation 的内存或打崩实例。

镜像 tag 里写死版本号，**不要用 `latest`**，也不要用 0.8.5 及以下。

## 12. 文档来源下沉进 `chunk.metadata`（一次刻意的反范式）

`Chunk` 上**没有** `Source` 字段——它是 `Document` 的属性。
但 `SearchResult` 内嵌的是 `Chunk`，**检索路径里根本没有 `Document`**。
不额外处理的话，检索结果就无法回答"这条内容出自哪儿"。

**做法**：`ingest` 在落库前把 `doc.Source` 写进每个片段的 `metadata`，检索时直接读。

这**违反了 #9 的原则**（能算出来的就不存第二份），是刻意为之。
判断依据是**访问路径**：

- `MatchedBy` 能在同一条记录内算出来 → 不存
- `Source` 要跨表 join 才拿得到 → 为一次检索多打一次库，代价明显更高

| 方案 | 代价 |
| --- | --- |
| **下沉（采用）** | 存储冗余；`document.source` 改了要重新回填 |
| 检索时 JOIN | 每次检索多一次查询；`AllChunks` 的 SQL 和内存索引都要跟着改 |
| 从 DTO 删掉该字段 | 零成本，但 Agent 彻底失去溯源能力 |

**两条边界必须守住**：

1. **不进 `IndexText()`**（#8）。文件路径里全是 `d`、`05`、`code` 这类噪声
   token，塞进索引文本只会污染 BM25 和向量，而且会让现有索引全部作废。
2. **为空时写"缺失"，不写空串**。空值和缺失必须能区分，
   否则将来做数据迁移时分不清"这份文档没有来源"和"来源是空字符串"。

> ⚠️ 下沉只对**新导入**的文档生效。修复之前入库的片段 metadata 里没有这个键，
> 检索出来 source 就是空的，要跑 `migrations/002_backfill_chunk_source.sql` 补齐。

## 附：这些决策的相互依赖

改任何一条之前，先看它连着谁：

```text
向量维度 (1024)
  └─ 受 pgvector HNSW 索引上限约束（2000）
  └─ 决定了 EmbeddingDim 常量、建表 DDL、pgvector-go 的类型注册
  └─ 改它 = 重建表 + 重建索引 + 重灌全量向量   ← 最贵

Embedding 模型 (bge-m3)
  └─ 决定了不能传 dimensions 参数
  └─ 决定了最大输入 8192 token
  └─ 决定了单次批量上限 32 条

分词方案 (bigram)
  └─ 决定了 BM25 的文档长度 |D| 和 avgdl 怎么算
  └─ 索引端和查询端必须是同一套规则，否则召回对不上

文档来源下沉 (#12)  ← 与 #8 是一条边界上的两个方向
  └─ 依赖 ingest 的写入路径 + migrations/002 的回填
  └─ 但来源**不能**进 IndexText()：进 metadata 可以，进索引文本不行
```

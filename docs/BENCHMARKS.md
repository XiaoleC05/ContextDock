## 优化（M7 · 2026-09-12）

### 先用 pprof 找热点，不猜

```bash
go test -bench . -benchtime 300x -cpuprofile=cpu.prof ./internal/retrieve/
go tool pprof -top -nodecount=20 cpu.prof
```

火焰图的前几名：

| 热点 | 占比 | 位置 |
| --- | ---: | --- |
| `tokenize.Tokenize` | 24.4% | 分词（字符串转换与 map 操作密集） |
| `VectorIndex.Search` | 20.0% | 向量检索 |
| `dot`（内联） | 10.7% | 余弦相似度内层循环 |
| `norm` | 4.9% | 模长计算 |
| **`tokenCount`** | **6.3%** | **每次查询都遍历词频 map 数 token 数** |

### 改了什么

`tokenCount` 那条是**设计缺陷，不是调优**：

```go
// 之前：每次查询、对每篇文档，重新遍历词频 map 数一遍 token
dl := float64(tokenCount(tf))                                  // O(词数)
score += ... / (f + m.k1*(1 - m.b + m.b*dl/m.avgdl))          // 每词项一次除法
```

这两个值**只和文档有关、和查询无关**，却在查询热路径上被反复计算。
改成索引时算好：

```go
// 现在：Index 时算一次，查询时直接取
norm := m.normCache[i]                                          // O(1)
score += ... / (f + norm)
```

### 结果

| 基准 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| **`BenchmarkBM25Search`** | **283,735** | **114,114** | **−60%（2.49×）** |
| `BenchmarkBM25Index` | 2,619,198 | 2,665,346 | +1.8%（噪声） |
| `BenchmarkVectorIndex` | 386,590 | 380,210 | −1.6%（噪声） |
| `BenchmarkVectorSearch` | 707,272 | 704,900 | −0.3%（噪声） |
| `BenchmarkFuseRRF` | 18,514 | 17,526 | −5.3%（噪声） |
| `BenchmarkHybridSearch` | 743,249 | 752,820 | +1.3%（噪声） |
| `BenchmarkTokenize` | 234,632 | 361,582 | **+54%（见下）** |

> ⚠️ **关于测量噪声**：`BenchmarkTokenize` 的两次测量差了 54%，
> 而它的代码**一行都没改**。这说明本机 benchmark 的噪声不小
> （CPU 睿频、后台负载、`-benchtime` 差异都会影响）。
>
> 所以只有**远大于噪声**的变化才算数。BM25Search 的 2.49× 是可信的；
> 其余几个百分之几的差异**不要当成结论**。
>
> 要更严格的数字，应该用固定频率、多次取中位数，或者干脆在 CI 上跑。

### 为什么 `BM25Index` 没有变快反而略慢

新增了一趟循环（算 `avgdl` 和 `normCache`）。这一趟是 O(文档数)，
相对于建词频 map 的 O(总词数) 可以忽略，`+1.8%` 在噪声范围内。
用一次性的一点索引成本，换查询路径上 2.49× 的加速，是划算的。

### 已知但**没有**优化的地方

`tokenize.Tokenize` 占了 24.4%，是现在最大的热点。没动它的原因：

- 它的开销主要来自 `strings.ToLower(string(word))` 和 `string(cjk[i:i+2])`
  这两处**必然的字符串分配**（分词器的输出契约就是 `[]string`）。
  要真正优化得改接口，而接口是被 BM25 和测试共同依赖的。
- 收益和风险不成比例：当前 1000 条片段的检索是百微秒级，
  对本地 MCP 场景（单用户、几十毫秒的容忍度）完全够用。
- **优化要有明确的收益对象**。在没有真实性能问题的场景下改接口，
  只是把复杂度换成了想象出来的速度。

如果将来文档量增长到检索变慢，这里是第一个该动的地方——
接口可以先加一个"往调用方提供的 buffer 里写"的变体，让热点路径复用切片。

## 小结

这次优化最大的收获不是那 2.49×，而是**火焰图纠正了我的直觉**：

我原以为瓶颈在向量计算（`dot` 看起来最显眼），
实际最大的浪费在一个 6 行的辅助函数里——它每次都重算早就该算好的东西。

**先测再改**这件事，说多少遍都不如自己踩一次。

## 基线（2026-09-12）

**参数**：切分 400 / 60，RRF k=60，候选倍数 3，topK=10 —— 全部是 v1.0.0 的默认值。

**语料**：5 份，196 个片段。指纹见 [`eval/corpus.json`](../eval/corpus.json)。

**评测集**：43 条查询（中文 15 / 英文 10 / 精确 token 8 / 同义改写 10）。

| 组 | 条数 | 词法 recall@10 | 向量 recall@10 | 融合 recall@10 | 融合 MRR | 融合 NDCG@10 |
| --- | --- | --- | --- | --- | --- | --- |
| zh | 15 | 0.767 | **0.933** | 0.800 | 0.617 | 0.639 |
| en | 10 | 0.400 | **0.900** | 0.700 | 0.431 | 0.501 |
| token | 8 | **1.000** | 0.750 | 0.875 | 0.688 | 0.737 |
| synonym | 10 | 0.000 | **0.400** | 0.100 | 0.014 | 0.033 |
| **总计** | **43** | 0.547 | **0.767** | 0.628 | 0.447 | 0.484 |

复现：

```bash
go run ./cmd/eval              # 表格
go run ./cmd/eval -json        # 机读
```

连跑三次输出**逐字节一致**（暖缓存）。冷缓存时嵌入接口的稳定性见「评测可复现性」一节。

### 三个可以直接读出来的事实

1. **词法通道在精确 token 上满分（1.000），在同义改写上零分（0.000）。**
   这正是两种检索方式「各有各的瞎子区」那句话的实测版本，也是当初选混合检索的动机。
2. **向量通道整体强得多**（0.767 vs 0.547），而且在中文组上接近满分。
3. **融合夹在两者之间**（0.628）——比词法好，比向量差。

第 3 条是整个里程碑最重要的发现，单独记在下一节。

### 这套评测的局限

写在数字旁边，而不是藏在附录里——**上面每一个数都受它们约束**：

| 局限 | 影响 |
| --- | --- |
| **只有 43 条查询** | 一条查询的权重是 2.3 个百分点。0.628 与 0.698 这种差别的置信度不高 |
| **单一标注者**（同一人的两次独立上下文） | 能挡住「照着检索结果标」的偏见，**挡不住这个人稳定的理解偏差**。标注复核的一致率是 25/33 |
| **语料是本仓库自己的文档**（3/5 份） | 标注者读过它们，语义重合度天然偏高，向量通道的成绩可能被高估 |
| **向量通道在这份语料上异常强**（中文组 0.933） | 融合的劣势可能被放大——弱通道（词法）相对更弱，挤占效应更明显 |
| **用内存存储** | 检索路径目前是暴力扫描，与存储无关，所以这不影响数字；但等 HNSW 真上线后，这个前提就不再成立 |
| **没有跨机器验证** | 只在 CI 与本机比对过，且只用了同一份嵌入缓存 |
| **「隔着一天重标」没有做** | 里程碑在一个工作日内完成，无法真实等待。这是已知缺口 |

复现基线：

```bash
go run ./cmd/eval -json > baseline.json
```

语料指纹钉在 [`eval/corpus.json`](../eval/corpus.json)；任一语料被改动，
评测器会直接报错退出，不会静默重跑。

## 证伪实验：单路 vs 融合（2026-09-12）

项目的整个设计都建立在「RRF 融合比任何单路都好」这个假设上。
**这个假设在这次实验里被证伪了。**

### 结论

在 v1.0.0 的默认参数下，融合的 recall@10 比**向量单路低 0.139**
（0.628 vs 0.767），而且在**四个子集上无一例外地不如单路最优者**：

| 组 | 融合 | 单路最优 | 增益 |
| --- | --- | --- | --- |
| zh | 0.800 | 向量 0.933 | **−0.133** |
| en | 0.700 | 向量 0.900 | **−0.200** |
| token | 0.875 | 词法 1.000 | **−0.125** |
| synonym | 0.100 | 向量 0.400 | **−0.300** |
| 总计 | 0.628 | 向量 0.767 | **−0.139** |

> 融合并非一无是处：它稳定地**击败较弱的那个通道**（0.628 vs 词法 0.547）。
> 问题在于它同时**被较强的通道拖累**——而在这份语料上，向量通道一直是较强的那一个。

### 为什么融合会变差

按 #40 的要求，先查原因再谈改实现。逐条展开融合结果之后，机制很清楚：

#### 逐条展开：sy-008「遇到故障就让进程直接退出，这种写法叫什么」

| 通道 | 相关内容的位置 | RRF 得分 |
| --- | --- | --- |
| 向量单路 | 第 5 名（cos 0.5323） | `1/(60+5)` = **0.0154** |
| 词法单路 | 未召回 | 0 |
| 融合第 4 名 | **两路都在第 28 名** | `2/(60+28)` = **0.0227** |

一个**两路都排 28 名**的片段，压过了一个**向量第 5 名、词法完全没召回**的相关片段。
于是那条相关片段掉出 top-10，这次查询从「命中」变成「未命中」。

两条线索指向同一个原因：

1. **k=60 把名次压得太平。** 第 1 名与第 28 名的贡献只差 `1/61` 与 `1/88`，
   而「被两路都召回」直接翻倍。当一路接近随机（本次的词法通道在 en / synonym 组就是如此），
   它的结果仍能拿到可观的分数，把强通路的结果挤下去。
2. **候选倍数放大了这个效应。** 倍数=1 时融合大致打平（总计 +0.023），
   倍数=3（生产默认）时降到 −0.139。多出来的 20 条弱通道候选，全是新的挤占者。

### 可检验的预测，以及它被证实

如果上面第 1 条是对的，那么**把 k 调小应当改善融合**。实测：

| RRF k | 融合 recall@10 | 词法 | 向量 |
| --- | --- | --- | --- |
| 10 | **0.698** | 0.547 | 0.767 |
| 30 | 0.628 | 0.547 | 0.767 |
| 60（默认） | 0.628 | 0.547 | 0.767 |
| 100 | 0.628 | 0.547 | 0.767 |

k 从 60 降到 10，融合提升 0.070（en 组 0.700→0.800，token 组 0.875→1.000），
**但不能翻转结论**——最好的融合仍然比向量单路低 0.069。

#### 顺带检查 README 里那句「k 在 10~100 区间内对 NDCG@10 的影响不到半个点」

| RRF k | 融合 recall@10 | 融合 NDCG@10 | 融合 MRR |
| --- | --- | --- | --- |
| 10 | 0.698 | 0.502 | 0.449 |
| 20 | 0.628 | 0.484 | 0.447 |
| 30 / 60 / 100 / 200 | 0.628 | 0.484 | 0.447 |

**方向对，幅度被低估了。** k 在 10~100 之间时 NDCG@10 的跨度是
0.484 → 0.502，即 **1.8 个百分点**（原说法是「不到半个点」）；
recall@10 的跨度则是 **7 个百分点**，比 NDCG 明显得多。

> ⚠️ 但 k≥20 那几行的指标**逐位相同**，这件事本身不能读成「k 再往上完全没影响」。
> 实测 k=20 与 k=200 下，43 条查询里有 28 条的融合 top-10 **顺序或成员确实不同**，
> 只是差异都落在尾部的 5~10 名，没有跨过「相关 / 不相关」的边界，
> 于是在这份 43 条的小评测集上被平均掉了。
>
> 一句话：**指标相同 ≠ 排序相同**。样本一旦变大，这个差别就可能显出来。

### ⚠️ 修正（同日，#44 的扫描结果）

上面「k 把名次压平是主因」的定位**不够准确**。融合参数扫描（下面那一节）显示：

```text
融合 recall@10        mult=1   mult=2   mult=4   mult=8
k=10                  0.791    0.721    0.744    0.698
k=30 / 60 / 100       0.791    0.721    0.651    0.674
────────────────────────────────────────────────────────
向量单路              0.767    0.767    0.767    0.767
```

两个更准确的结论：

1. **主因是候选倍数，不是 k。** mult 从 1 加到 4，融合掉 0.140；
   而在 mult=1 时，k 从 10 到 100 **完全不影响结果**（四行都是 0.791）。
2. **mult=1 时融合是赢的**（0.791 vs 向量 0.767，+0.023）。
   项目原本的假设在最保守的候选设置下**成立**。

所以问题不是「RRF 不行」，而是「**把候选池放大之后，弱通道的噪声压过了强通道的信号**」。
生产默认 mult=3 恰好落在有害区间里。

下面那一节有完整矩阵。

### 这个结论的边界

⚠️ **不要把它读成「RRF 是错的」。** 它证明的是：

- 在**这份语料 + 这 43 条查询 + 这套参数**上，融合不如向量单路
- 机制是名次压缩 + 弱通道的挤占，并且这个机制是可复现、可解释的

它**没有**证明：

- 换一份语料仍然如此。本次语料只有 5 篇文档、196 个片段，而且**向量通道异常强**
  （中文组 0.933）——查询是标注者读过这些文档之后写的，语义重合度天然很高
- 融合在其他 k / 其他候选策略下也一定输。#44 的参数扫描要接着查
- 词法通道没有价值。它在精确 token 组是**唯一**能拿满分的通道（1.000 vs 0.750），
  而 token 组正是「错误码、函数名、配置项」这类不能模糊匹配的场景

> 换句话说：**问题可能不在 RRF，而在于「不管两路强弱、一律等权」这件事。**
> 一个明显值得测的方向是让权重随通道质量变化，但那要先有本节的数字做基线。

## 失败案例分析（2026-09-12）

基线（默认参数）下，43 条查询里有 16 条至少漏了一条期望，共 16 条未召回的期望。
指标只说「差多少」，这一节逐条追「为什么差」。

复现：

```bash
go run ./cmd/eval -json -detail    # 报告里带 retrieved：三路各自实际返回了什么
```

### 失败原因分布

先把「哪条通道找到了」当作第一刀——它把失败劈成**两个机制完全不同**的类：

| 类型 | 条数 | 占比 | 特征 |
| --- | --- | --- | --- |
| **A 融合挤占** | 8 | 50% | 单路找到了，融合把它挤出了 top-10 |
| **B 目标片段主题稀释** | 7 | 44% | 两路都没找到，目标所在片段是多条目列表 / 表格 |
| C 其他召回失败 | 1 | 6% | 两路都没找到，片段是普通段落 |

> ⚠️ A 与 B 只差 1 条，**50% 与 44% 的差距在这个样本量下没有意义**。
> 真正有意义的区分是「融合层的锅」还是「召回层的锅」——它们是 8 : 8。

### A 类：融合挤占（8 条）

`zh-010` `zh-014` `en-004` `en-006` `sy-003` `sy-004` `sy-008` `tk-003`

这 8 条**检索本身是成功的**：至少有一条单路把它们放进了 top-10，
是融合把它们挤了出去。机制与原因已在
[证伪实验](#证伪实验单路-vs-融合2026-09-12) 中定位：

```text
tk-003「CGO_ENABLED=0 编译会失败吗」
  词法通道：找到了目标（recall 1.00）
  融合：    recall 0.00 —— 被「两路都召回」的噪声挤掉
```

**结论：这 8 条不需要改检索，需要改融合。**

### B 类：目标片段主题稀释（7 条）

`zh-011` `en-002` `sy-001` `sy-002` `sy-006` `sy-009` `sy-010`

这 7 条两路都召不回来。它们有一个共同点：**目标所在的片段里塞着好几个互不相关的条目**。
例如 `sy-002` 的目标落在 README「已知限制」那一段——那个 397 字的片段里同时装着
无相关性阈值、中英混合、PDF 支持、代码块切碎、暴力扫描、BM25 内存索引、切分参数、
并发写入保护**八件互不相干的事**。

对向量通道来说，这个片段的向量是八个主题的**平均值**，对其中任何一个都不像；
对词法通道来说，BM25 的长度归一化本来就在惩罚长片段，而它又摊薄在八个主题上。

#### 这不是编出来的解释——有对照

只看「未召回」的比例会误导：多条目片段本来就多。控制片段长度之后：

| 目标所在片段（只取 300–399 字） | 标注数 | 两路均未召回 | 比例 |
| --- | --- | --- | --- |
| 列表 / 表格项 0–2 条 | 10 | 0 | **0%** |
| 列表 / 表格项 3 条以上 | 24 | 7 | **29%** |

长度被控制住之后，效应仍然存在，而且是 0% 对 29% 这种量级。

> ⚠️ **但样本很小，别过度解读。** 10 条与 24 条的分组，挪动一两条就会明显改变比例。
> 这足以支撑「值得先去改切分」这个**决策**，不足以支撑「多条目片段必然召不回」这个**结论**。
> #43 的切分参数扫描会用完整的 5×4 矩阵来验它。

### 修复优先级

| 优先级 | 修什么 | 依据 |
| --- | --- | --- |
| **1** | **融合层**（#40 已定位机制） | 8/16 的失败是融合挤占；机制已查明、改动局限在融合层；而且**收益上限明确**——追平向量单路即 recall +0.139 |
| **2** | **切分：列表 / 表格感知** | 7/16 的失败指向多条目片段；与 #47（代码块 / 表格感知切分）天然重合，不用另开一条路；对照实验支持 |
| **3** | 其他 | 只剩 1 条，不值得为它单独设计 |

**为什么融合排第一**：它的收益是**可计算的**（+0.139），而切分改造的收益只能估。
先做收益确定的那件事。

**为什么不先做切分**：切分一改，所有片段边界都变，
上面所有基线数字都要重跑——先改融合可以省一次完整的基线重跑。

## 切分参数扫描（2026-09-12）

MaxRunes ∈ {200, 300, 400, 600, 800} × Overlap ∈ {0, 30, 60, 120}，共 20 组。
每组都记录质量与成本两侧的数字——**只看 recall 排序会选出病态参数**。

复现：

```bash
go build -o bin/eval.exe ./cmd/eval
for mr in 200 300 400 600 800; do for ov in 0 30 60 120; do
  ./bin/eval.exe -json -quiet -maxrunes $mr -overlap $ov > sweep_${mr}_${ov}.json
done; done
```

> 耗时数字取自**暖缓存**的第二轮。第一轮要拉嵌入，网络往返会淹没切分与建索引的成本；
> 报告里的「嵌入缓存命中」就是用来判断这一点的。

### 完整矩阵

#### 融合 recall@10

| MaxRunes \ Overlap | 0 | 30 | 60 | 120 |
| --- | --- | --- | --- | --- |
| 200 | 0.674 | 0.605 | 0.651 | 0.709 |
| 300 | 0.628 | 0.674 | 0.721 | **0.744** |
| 400（旧默认） | 0.674 | 0.651 | 0.628 | 0.698 |
| 600 | 0.744 | 0.744 | **0.767** | 0.744 |
| 800 | 0.698 | 0.698 | 0.744 | 0.721 |

#### 片段总数

| MaxRunes \ Overlap | 0 | 30 | 60 | 120 |
| --- | --- | --- | --- | --- |
| 200 | 324 | 361 | 425 | **1073** |
| 300 | 229 | 242 | 258 | 311 |
| 400 | 184 | 188 | 196 | 212 |
| 600 | 144 | 146 | 148 | 149 |
| 800 | 124 | 124 | 124 | 126 |

#### 索引体积

| MaxRunes \ Overlap | 0 | 30 | 60 | 120 |
| --- | --- | --- | --- | --- |
| 200 | 1.34 MB | 1.50 MB | 1.77 MB | **4.44 MB** |
| 300 | 0.97 MB | 1.03 MB | 1.10 MB | 1.33 MB |
| 400 | 0.80 MB | 0.82 MB | 0.85 MB | 0.93 MB |
| 600 | 0.64 MB | 0.65 MB | 0.66 MB | 0.67 MB |
| 800 | 0.56 MB | 0.56 MB | 0.57 MB | 0.58 MB |

导入并建索引耗时（暖缓存）在 14 ~ 69 ms 之间，与片段数同向。

### 结论一：这份评测集分辨不出切分参数的优劣

这是最要紧的一条，也是事先没料到的。

融合 recall 的全场跨度是 0.628 ~ 0.767，看着不小。但：

- 43 条查询里，**一条查询的价值是 0.023**。整个跨度只相当于 **6 条查询**
- 以 p≈0.7、n=43 估算，标准误约 **0.07**；0.139 的跨度大约是两个标准误
- 而行与行之间**根本不单调**：400/60（旧默认）0.628 低于 200/120（片段最小）0.709，
  600/60（片段最大之一）0.767 又最高

**这 20 组之间的差别，与「换一批同样数量的查询、排名会重排」的幅度处在同一量级。**

> ⚠️ **所以不能拿这张表选参数。** 600/60 确实是最大值，但它与第二名只差 2 条查询——
> 按最高值去选，等于在噪声上做拟合。这正是 issue 警告的「凭感觉选中间值」的反面版本：
> 不是凭感觉，而是**凭一个测不准的量**。

### 结论二：成本侧的趋势是单调且巨大的

| 从 → 到 | 片段数 | 索引体积 |
| --- | --- | --- |
| 800/0 → 200/0 | 124 → 324（2.6×） | 0.56 → 1.34 MB（2.4×） |
| 200/120（最碎） | **1073** | **4.44 MB** |

issue 里那条警告被精确量化了：

```text
200/120  vs  200/0
  recall   0.709  vs  0.674      ← 只高 0.035（约 1.5 条查询）
  片段数    1073  vs   324        ← 高 3.3 倍
  体积     4.44MB vs  1.34MB     ← 高 3.3 倍
```

**用 3.3 倍的索引换 1.5 条查询的召回，而且那 1.5 条还测不准。** 这就是病态参数的样子。

### 结论三：收益拐点

按**成本**看拐点明确：MaxRunes 从 200 加到 600，片段数从 324 降到 144（−56%）；
从 600 再加到 800 只降到 124（−14%）。再往上已没有多少可省。

按**质量**看没有拐点——曲线在噪声范围内是平的。

两者的交点落在 600 附近：

| 配置 | 片段数 | 索引体积 | 融合 recall | 融合 NDCG@10 |
| --- | --- | --- | --- | --- |
| 400/60（旧默认） | 196 | 0.85 MB | 0.628 | 0.484 |
| **600/60** | **148** | **0.66 MB** | **0.767** | **0.530** |
| 800/60 | 124 | 0.57 MB | 0.744 | 0.503 |

600/60 在两边都不吃亏：比 400/60 少 24% 的片段、少 22% 的体积，质量数字也更高。

> 但请连着结论一读：**质量那一列站不住**。#46 落新默认值时，依据必须是
> 「成本明显更低、质量未见下降」，**不能**是「实测最优」。

### 顺带：扫描本身暴露了一个真 bug

第一轮扫描里 `Overlap=0` 与 `Overlap=60` 的数据**逐行完全相同**。查下去发现
`chunk.Config.normalize()` 把 `OverlapRunes == 0` 当成「未设置」回落成了 60——
**用户根本没有办法关掉重叠**。

这违反的是本项目自己写在 `types.Chunk.Ordinal` 注释里的规则：
「0 是合法值……它不能像 ID 那样被当作『未设置』的哨兵」。

已修：`OverlapRunes` 改用**负数**表示未设置。修复前后：

| 配置 | 修复前片段数 | 修复后片段数 |
| --- | --- | --- |
| 400/0 | 196（假的，实际按 60 切） | **184** |
| 200/0 | 425（假的） | **324** |

> 如果不是这次扫描要求逐个参数都跑一遍，这个 bug 会一直藏着——
> 它不影响默认配置，只在有人真想关掉重叠时现形，而那时他会以为「关了也没区别」。

## 标注复核（2026-09-12）

评测集的**标注质量**决定了所有质量数字的有效性，而标注是人做的。
所以标完之后做了一次复核，并把结果如实记在这里——**包括不好看的部分**。

### 复核方式

由**另一次独立会话**在相同规则下重新标注一遍：

- 看不到原始标注，也看不到原始 `note`（否则只是抄一遍）
- 只拿到「查询文本 + 语料原文 + 判定规则」
- 共复核 **33 条**（中文 15 + 英文 10 + 精确 token 8）

**同义改写组的 10 条未参与复核。** 那组的约束是「与目标片段零字面重叠」，
需要跑分词器逐 token 比对，人眼判不了——它由校验器里的自动化检查兜底，
比人工复核更严格。

### 结果

| 口径 | 一致 | 一致率 |
| --- | --- | --- |
| 严格区间重叠（复核引文与原标注区间相交） | 25 / 33 | **75.8%** |
| 同上，但按复核结果修正了 1 条原标注之后 | 25 / 33 | 75.8% |

> ⚠️ **怎么读这个 75.8%**：它不是「四分之一的标注是错的」。
> 复核者选中的是**相邻段落**时，区间不相交，但两边都答对了问题。

### 那 8 条「不一致」逐条看过之后

| 类型 | 条数 | 说明 |
| --- | --- | --- |
| 相邻段落 | 5 | 复核者选的是紧邻的上一句或下一句，例如 zh-014 与 en-006 恰好互换了相邻的两句 |
| 同一条表格记录的不同单元格 | 1 | en-009：同一行里「默认 40 偏低」与「建议 100 起步」两格 |
| 等价来源 | 1 | en-005：「HNSW 上限 2000 维」在 README、DESIGN、PITFALLS 三处都有 |
| **原标注确实更弱** | **1** | en-008：原标注选的是章节标题（只提到两个宏的名字），复核者选的是讲用法的正文 |

最后一条已经**按复核结果改正**。其余 7 条保留原标注：它们不是错，只是同一处答案的
不同切法，而原标注更贴近问题的问法。

### 这次复核的局限

> ⚠️ **「那 8 条到底算不算一致」是我自己判的。**
>
> 我是原始标注者，有把结果往「一致」方向解释的动机。这一步**不是独立的**，
> 所以上面那张分类表应当被当作**需要复核的意见**，而不是已证实的事实。
> 独立的部分只有严格区间重叠那一个数字：**25/33**。

其余局限：

- 样本只有 33 条，一条的权重就是 3 个百分点，比率本身不精确
- 复核者与原标注者是同一个人（同一次会话的不同上下文）——
  这能挡住「照着检索结果标」的偏见，**挡不住这个人稳定的理解偏差**
- 原定的「**隔天**重标」没有做：本里程碑在一个工作日内完成，无法真实等待一天。
  这是这套评测目前的一个**已知缺口**，不应被当作已验证的稳定性

### 结论

标注一致性**够用但不宽裕**。足以支撑「A 配置比 B 配置好」这类相对比较，
**不足以**支撑「召回率是 0.73」这类绝对断言。

## 融合参数扫描（2026-09-12）

RRF k ∈ {10, 30, 60, 100} × 候选倍数 ∈ {1, 2, 4, 8}，共 16 组。
切分固定为 400/60（旧默认），这样变动的只有融合参数。

复现：

```bash
go build -o bin/eval.exe ./cmd/eval
./bin/eval.exe -json -quiet -k 60 -mult 3 > /dev/null   # 先预热嵌入缓存
for k in 10 30 60 100; do for m in 1 2 4 8; do
  ./bin/eval.exe -json -quiet -k $k -mult $m > fuse_${k}_${m}.json
done; done
```

> 延迟必须在**暖缓存**下比较，否则网络往返会盖掉检索本身的差别。

### 完整矩阵

#### 融合 recall@10

| k \ mult | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| 10 | **0.791** | 0.721 | 0.744 | 0.698 |
| 30 | **0.791** | 0.721 | 0.651 | 0.674 |
| 60（默认） | **0.791** | 0.721 | 0.651 | 0.674 |
| 100 | **0.791** | 0.721 | 0.651 | 0.674 |
| **向量单路（基准）** | 0.767 | 0.767 | 0.767 | 0.767 |

#### 融合 NDCG@10

| k \ mult | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| 10 | 0.533 | 0.514 | 0.529 | 0.516 |
| 30 | 0.533 | 0.514 | 0.495 | 0.501 |
| 60（默认） | 0.533 | 0.514 | 0.495 | 0.501 |
| 100 | 0.533 | 0.514 | 0.495 | 0.501 |

#### 检索延迟 P50 / P95（毫秒）

| k \ mult | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| 60 P50 | 0.50 | 0.51 | 0.49 | 0.51 |
| 60 P95 | 0.66 | 0.74 | 1.00 | 0.76 |

### 结论一：候选倍数是主因，k 是次因

`mult` 从 1 加到 4，融合 recall 掉 0.140；而 `k` 在 **mult=1 时从 10 到 100 完全不影响结果**
（四行都是 0.791）。

k 只在候选被放大之后才起作用，而且方向是「**k 越小越好**」——
这与「k 越小越赢者通吃、k 越大越扁平」的定义一致，也解释了为什么
候选一多（噪声一多），扁平化就放大伤害。

### 结论二：mult=1 时融合**赢**了

| 设置 | 融合 | 向量单路 | 差 |
| --- | --- | --- | --- |
| mult=1（k 任意） | **0.791** | 0.767 | **+0.023** |
| mult=2 | 0.721 | 0.767 | −0.047 |
| mult=3（生产默认） | 0.628 | 0.767 | −0.139 |
| mult=4 | 0.651 | 0.767 | −0.116 |
| mult=8 | 0.674 | 0.767 | −0.093 |

**这是对 #40 那条结论的重要修正。** 「RRF 融合不如单路」不是普遍成立的，
它只在**候选被放大之后**成立。在最保守的设置（两路各取 top-10，不放大）下，
融合是**唯一一个超过向量单路**的配置。

> ⚠️ 但 +0.023 只相当于 **1 条查询**，在 43 条样本上是噪声。
> 准确的说法是「mult=1 时融合与向量单路打平，不再明显吃亏」，
> **不是**「融合更好」。

### 结论三：mult 的代价是质量，不是速度

P50 在 0.49 ~ 0.51 ms 之间，P95 在 0.66 ~ 1.00 ms 之间，**跨 8 倍候选没有可测变化**。

原因是规模：196 个片段 × 8 倍候选 = 1568 次余弦相似度，对这种规模的暴力扫描
仍然是亚毫秒级。而计时器的分辨率大约就在 0.5 ms 这个量级，测不出差别。

> **所以不能拿「延迟没变」当作「放大候选没代价」的理由。**
> 代价体现在**质量**上（−0.14 recall），而质量在这个场景里比 0.5ms 重要得多。
> 等片段规模上到十万级、HNSW 真正上线之后，候选倍数的延迟成本才会显现出来。

### 结论四：README 那句「k 在 10~100 区间内对 NDCG@10 的影响不到半个点」

| mult | NDCG@10 在 k∈{10,30,60,100} 上的跨度 |
| --- | --- |
| 1 | 0.000 |
| 2 | 0.001 |
| 4 | 0.035 |
| 8 | 0.015 |

**大体成立，但要看 mult。** mult 小时跨度近乎为零（原说法完全对）；
mult=4 时到 3.5 个百分点，就超出「不到半个点」了。

原文没有附这个前提，因为当时还没有评测数据。现在补上：
**「k 影响很小」这个结论是在候选不放大时成立的；候选一放大，k 就开始起作用。**

### 该改什么

**把候选倍数从 3 降下来。** 依据：

- 它是这份评测里**唯一一个被证明会造成大幅损失**的参数（−0.14 recall）
- 降到 1 之后融合不再吃亏，而且**不增加任何成本**（延迟没变化）
- 但 `#46` 落新默认值时应当留意：mult=1 与 mult=2 之间还差 0.07，
  真实最优值可能在两者之间，而这份 43 条的评测集分辨不出

> ⚠️ 同样别把 mult=1 当成「测出来的最优」。它在 43 条上是最大值，
> 但第二名只差 1~3 条查询。要断言它最优，得先把评测集做大。

## 分词方案对比（2026-09-12）

对比 CJK 部分的三种切法。切分固定 400/60，融合固定 k=60 / mult=3。
**只看词法通道**——分词只影响 BM25，向量通道对同一份文本取同一批向量，不受影响
（下表里向量 recall 三行完全相同，就是这条的验证）。

复现：

```bash
go build -o bin/eval.exe ./cmd/eval
for s in bigram unigram both; do ./bin/eval.exe -json -quiet -tokenize $s > tok_$s.json; done
```

### 结果

| 方案 | 词法 recall@10 | 词法 NDCG@10 | 融合 recall@10 | 向量 recall@10 |
| --- | --- | --- | --- | --- |
| **bigram（默认）** | 0.547 | 0.442 | 0.628 | 0.767 |
| unigram | **0.605** | **0.463** | **0.721** | 0.767 |
| both | 0.523 | 0.408 | 0.674 | 0.767 |

按子集看词法通道：

| 组 | bigram | unigram | both |
| --- | --- | --- | --- |
| zh | 0.767 | **0.800** | 0.767 |
| en | 0.400 | 0.400 | 0.400 |
| token | **1.000** | **1.000** | 0.875 |
| synonym | 0.000 | **0.200** ⚠️ | 0.000 |

### 结论一：unigram 的优势是**假象**

unigram 看起来全面更优（词法 +0.058，融合 +0.093）。但它在
**同义改写组**上拿到了 0.200——而那一组是**特意构造成与目标片段零字面重叠**的，
本来就不该被词法通道命中。

逐条查了它是怎么命中的：

```text
sy-002「逐个比对的开销还划算吗」
  目标原文：**内存检索是暴力扫描**
  bigram 切查询：逐个 个比 比对 对的 的开 开销 还划 划算 算吗  → 一个都不在原文里
  unigram 切查询：逐 个 比 对 的 开 销 还 划 算 吗            → 比 / 对 / 的 / 算 全都在
```

**单字方案靠「比」「对」「的」「算」这类常用字撞上了目标。** 而它词法通道
实际返回的前两名与此毫无关系（一个是讲 `server_test.go` 的段落，一个是讲
Qwen3 截断的表格）。

> ⚠️ 这条同时暴露了评测集的一个边界：**「零字面重叠」这个保证是 bigram 专属的**。
> 换 unigram 之后单字会撞上，同义改写组就不再只测向量通道了。
> 已记进 [EVAL.md](EVAL.md)。

所以 unigram 的 +0.058 **不是召回能力的提升，而是噪声**。它在 zh 组上多出的
0.033 也只相当于 1.4 条查询，在 43 条样本里分辨不出来。

### 结论二：「两个都要」反而最差

`both`（单字 + bigram）在词法上是三种方案里最差的（0.523），
连精确 token 组都从 1.000 掉到 0.875。

直觉上「多给一些检索点总不会更差」，但 BM25 不是这么工作的：

- 词典大一倍 → 常用单字的 df 很高 → IDF 很低，几乎不贡献分数
- 每条片段的 token 数近乎翻倍 → 长度归一化（b=0.75）把分数整体压低
- 结果是**真正有区分度的 bigram 被大量无信息的单字稀释掉了**

### 结论三：DESIGN §3 的选型站得住，但依据要更新

原文给的理由是「零依赖、约 20 行、中文本登录词问题天然消失」——
那几条关于**工程成本**的理由依然成立，这次也没有被推翻。

但**质量层面**当时没有证据，现在有了，而且是：**bigram 并不比 unigram 召回更高**。
保留 bigram 的真正依据是另外两条：

1. **它不用常用单字制造假命中**（synonym 组 0.000 vs 0.200）
2. **它在精确 token 上是并列最强的**，而 "both" 会把它拖到 0.875

也就是说：**bigram 的价值不在「多召回」，而在「少误召」**。
这个区别在原文里没有说清楚，已补进 DESIGN §3。

## 标定结果落地（2026-09-12）

四次扫描（切分 / 融合 / 分词 / 失败分析）之后，逐个决定默认值的去留。
**每个值都附依据；维持原样的也写下来**——那同样是结论，而且能防止后人反复重测。

### 改了：候选倍数 3 → 1

| | 旧默认 | 新默认 |
| --- | --- | --- |
| `retrieve.DefaultCandidateMultiplier` | 3 | **1** |

**依据**：融合参数扫描。倍数从 3 降到 1 时 recall 从 0.628 升到 0.791（+0.163，
约 7 条查询），而且**不增加任何成本**——延迟在 0.49~0.51ms 之间没有可测变化。

**代价要说清**：倍数=1 有一个结构性盲区——一条排在向量第 15 名、词法第 25 名的
结果，两路都不会把它送进融合。这个盲区在机制上确实存在，
但实测里噪声的伤害更大。

**变更前后的整体成绩**：

| 组 | 词法 recall | 向量 recall | 融合 recall（旧） | 融合 recall（新） |
| --- | --- | --- | --- | --- |
| zh | 0.767 | 0.933 | 0.800 | **0.933** |
| en | 0.400 | 0.900 | 0.700 | 0.800 |
| token | 1.000 | 0.750 | 0.875 | **1.000** |
| synonym | 0.000 | 0.400 | 0.100 | **0.400** |
| **总计** | 0.547 | 0.767 | 0.628 | **0.791** |

| 指标 | 旧默认 | 新默认 |
| --- | --- | --- |
| 融合 recall@10 | 0.628 | **0.791** |
| 融合 NDCG@10 | 0.484 | **0.533** |
| 融合 MRR | 0.447 | **0.462** |
| 检索 P50 / P95 | 0.50 / 1.00 ms | 0.50 / 1.10 ms |

**最重要的变化**：改之前融合在四个子集上**全部**不如单路最优者；
改之后它在 zh / token / synonym 三组上**追平**了单路最优，只在 en 组仍差 0.100。
总计从「比向量低 0.139」变成「比向量高 0.023」。

> ⚠️ 但 +0.023 只相当于 1 条查询。准确说法是「不再明显吃亏」，
> **不是「融合更好」**。要断言融合确实更优，得先把评测集做大。

### 维持原样：切分 400 / 60

**依据**：切分参数扫描的 20 组里，融合 recall 在 0.605 ~ 0.767 之间，
而一条查询的价值就是 0.023——**整个跨度只相当于 7 条查询，且完全不单调**
（400/60 是 0.628，200/120 是 0.709，600/60 是 0.767）。

**测不出差别，就不动它。** 600/60 在成本上更省（片段数 −24%、体积 −22%），
但这个收益在当前规模下是 0.85MB → 0.66MB，无关紧要；
而改动切分参数会让**所有片段边界和全部历史基线作废**，需要完整重跑。
收益与代价不成比例。

> 等到语料规模大一个数量级（比如十万级片段），成本的绝对值变得重要时，
> 这张扫描表的成本侧数据可以直接拿来用——那时它才真正有价值。

### 维持原样：RRF k = 60

**依据**：在候选倍数=1 下，k 从 10 到 100 **完全不影响结果**（四行都是 0.791）。
k 只在候选被放大时才起作用，而放大已经被关掉了。

### 维持原样：分词方案 bigram

**依据**：分词方案对比。unigram 的数字更高（词法 0.605 vs 0.547），
但那个优势全部来自**常用单字的噪声匹配**——它在「零字面重叠」的同义改写组上
拿到 0.200，而那一组本不该被词法通道命中。

### 没有改、也没有测的

- **k1 / b（BM25 的两个参数）**：`WithParams()` 早就支持覆盖，
  但这次没扫。它们对词法通道的影响可能比分词方案更大，值得单独一轮实验。
- **topK**：它是**用户可见的接口参数**，不是一个该被"标定"的实现细节——
  Agent 要几条就给它几条，不该由我们替它定一个"最优值"。

## 代码块 / 表格感知切分（2026-09-12，#47）

### 改了什么

切分时识别两类**保护区**，不从中间切开：

- **围栏代码块**（``` 或 ~~~），含开闭标记行
- **表格**：连续 ≥3 行以 `|` 开头

处理策略：

1. 切分点落在保护区中间时，**退到保护区起点**，让整块从下一片干净地开始
2. 在保护区起点结束时，**下一片不做重叠**——否则重叠会把起点拉回块前，
   刚保护好的整块又放不进下一片的窗口里
3. 块本身超过 `MaxRunes` 时物理上无法整体保留，退而求其次：
   在块内的**行边界**切；连行边界都没有（超长单行）时只能切满一片

### 质量：**没有可测的提升**

同一份评测集、同一套参数（切分 400/60，k=60，倍数=1）：

| | 片段数 | 融合 recall@10 | 融合 NDCG@10 |
| --- | --- | --- | --- |
| 改前 | 196 | 0.791 | 0.533 |
| 改后 | 203 | **0.791** | 0.515 |

**recall 完全相同**，NDCG 差 0.018（不到一条查询）。按子集看，
en 组 +0.100、synonym 组 −0.100，正好抵消。

> **如实记录：这项改动在当前评测集上没有得到可测的质量收益。**
> 片段数反而多了 3.6%（保护区把边界推开时会产生更短的片）。

### 那为什么保留

因为它修的是一个**确定存在的结构缺陷**，而不是一个指标问题：

```text
改前：一个讲 badge 的片段，末尾孤零零挂着 "```text" 这半行
      ——围栏开标记被留在了完全不相关的上下文里
改后：该片段在区块之前结束，开标记落在包含图表开头的那个片段里
```

守护它的是 `internal/chunk` 里的四条测试，而不是 recall 数字：

| 测试 | 守的是什么 |
| --- | --- |
| `TestFencedBlockStaysWholeWhenItFits` | 放得下的围栏块必须被某个片段完整包含 |
| `TestOversizedFencedBlockBreaksOnlyAtLineBoundaries` | 超长块只能在行边界切 |
| `TestTableRowsStayTogether` | 表格不被从中间切开 |
| `TestFreestandingPipesAreNotTable` | 阈值（≥3 行）不误伤正文里的管道符 |

> ⚠️ 这些指标测不出来，**不代表缺陷不存在**——只说明这 43 条查询
> 没有一条的答案正好落在被切坏的碎片上。等评测集变大、或 #51 逐项量化时，
> 这个判断应该被重新检验。**不为了「做了」而保留**这条原则同样适用：
> 如果将来证明它只带来复杂度，就该回退。

### 过程中的三个真 bug（都是测试/变异测试逼出来的）

写完之后先写测试，测试立刻红了三次：

1. **切分空转**：允许把切分点退到「任何 `region.start > pos`」的位置，
   而下一片起点是 `end - overlap` —— 退到块首之后又退回到块首之前，
   两次调用算出同一个 `end`，全靠 `next = pos + 1` 兜底一个字符一个字符地挪。
   实测 545 字符切出 **47 片**（合理值约 8 片），**而不报任何错**。
2. **兜底写反**：断点太靠近起点时写成 `cut = minEnd`，
   下一片起点正好是 `pos + 1` → 每轮只前进一个字符，切成 27 个碎片。
   正确做法是在 `(minEnd, limit]` 里重新找断点。
3. **裁剪顺序**：判断「是否切在块首」时用的是**裁剪尾部空白之后**的位置，
   而块首往往紧跟在换行之后，裁剪会把它退到块前，判断永远不成立。

### 一个死分支，是变异测试发现的

`cutPoint` 里原本有一条「断点落在保护区中间、整块放得下就整块带走」的分支。
它的条件是「`regionAt(limit)` 且 `r.end-pos <= MaxRunes`」——但前者蕴含
`r.end > limit`，后者等价于 `r.end <= limit`，**两个条件不可能同时成立**。

把它整条改成 `false`，11 条测试一条都没红，才暴露出来。
删掉之后测试仍然全绿，确认它确实是多余的。

> 「优先整体保留」不是靠「把整块塞进当前片」实现的，
> 而是靠「退到块首」+「不在块首回退重叠」这两条配合。

## 重叠起点吸附行边界：试了，无用，已回退（2026-09-12，#48）

### 问题

重叠是**盲退固定字符数**（默认 60），不找行边界。于是硬截断出来的片段常从半行
开始——实测能见到以 `───────────┘` 开头的片段。

### 试了两种方向

| 方向 | 做法 | 对重叠的影响 |
| --- | --- | --- |
| **朝文末吸附** | 回退点到 `end` 之间找第一个行首 | 重叠**变短**，极端时趋近于零 |
| **朝文首吸附** | 回退点往前找最近的行首 | 重叠**变长**（最多 200 字符） |

> issue 里写的是第一种（"实际重叠长度可能短于配置值"）。第二种是补做的对照——
> 因为第一种让指标变差时，得先排除「是方向选错了」这个可能。

### 结果：两种方向，**没有一次更好**

同一份评测集，四个切分参数各跑一遍：

| 切分 | 不吸附 recall | 朝文末吸附 | 朝文首吸附 |
| --- | --- | --- | --- |
| 400/60 | **0.791** | 0.744 | 0.744 |
| 600/60 | **0.837** | 0.837 | 0.837 |
| 300/120 | **0.814** | 0.791 | 0.791 |
| 800/30 | **0.837** | 0.837 | 0.837 |

**8 组对比里，不吸附一次都没输过；一半的对比里吸附更差。**

两种吸附方向给出的 recall **逐位相同**（400/60 都是 0.744，600/60 都是 0.837），
这本身就是一条线索：伤害不来自重叠的长短——一个缩短它、一个延长它，
结果一样。

### 机制

> **吸附会同时移动片段的语义边界，而不只是「把起点对齐到行首」。**

片段的内容决定了它的向量，向量决定了它排第几。把起点挪几十个字符，
片段的内容就变了，排名随之变化——而排序变差和变好的概率并不对等：
原本卡在 top-10 边缘的那几条会被挤出去，而它们本来正是在边界上的。

换句话说：**「从半行开始」是可读性问题，「答案被切在接缝处」是能不能取到的问题。**
重叠存在的全部意义就是防后者。为了前者去动后者，方向就反了。

### 决定：回退

`chunkSection` 保持**盲退固定字符数**。回退处留了一段注释说明这段历史，
免得后人再"顺手修一下"。

**README 的「重叠起点不吸附行边界」那条已知限制保留**，但它的性质变了：

- 以前是「**还没做**」
- 现在是「**试过两种做法，实测都更差，不做**」

这两者完全不同。后者是结论，前者只是待办。

> ⚠️ 样本只有 43 条查询，单次对比的置信度不高。但这次是 **8 组对比一致**，
> 而且机制清楚——不是靠单点数据下的结论。

## 上下文扩展（2026-09-12，#49）

### 做了什么

命中片段时，顺带返回它**前后相邻片段的一小段摘要**：

- 新增配置 `CONTEXTDOCK_CONTEXT_NEIGHBORS`（默认 1，0 = 关）
- MCP 结果里多出 `context_before` / `context_after` 两个字段
- 各**截断到 120 字符**：前一段取**尾部**、后一段取**头部**

`Chunk.Ordinal` 和偏移量的注释里早就写着它们的用途是"上下文扩展"，
但一直没实现。这次补上了。

### 为什么是截断的、为什么取那一头

命中片段常常只写着「运行 go build」，单独看不知道在讲什么。

- **截断而不是整段带出**：10 条结果各带两整段（每段可达 400 字）会让输出
  膨胀近三倍，而那些内容**大多是重复的**——相邻片段本来就重叠着 60 个字符。
  Agent 的上下文窗口是稀缺资源。
- **前一段取尾、后一段取头**：那才是紧挨着命中的一头。取前一段的头部
  等于给 Agent 看一段它根本接不上的话，比不给还糟。

### 收益：四组配置全部非负

评测指标是「把相邻片段也算进来之后」的召回率。它回答的是
**Agent 拿到的东西够不够完整**，而不是检索排得好不好——
所以相邻片段不参与排序、也不计入 MRR / NDCG（给它们编一个名次
会让指标变成数字游戏）。

| 切分 | 融合 recall（仅命中 → 含相邻片段） | 向量 | 词法 |
| --- | --- | --- | --- |
| 400/60 | 0.791 → **0.814** (+0.023) | 0.767 → 0.814 | 0.547 → 0.593 |
| 600/60 | 0.837 → 0.837 (+0.000) | 0.767 → 0.791 | 0.547 → 0.651 |
| 300/120 | 0.814 → **0.837** (+0.023) | 0.837 → 0.860 | 0.523 → 0.570 |
| 800/30 | 0.837 → **0.860** (+0.023) | 0.814 → 0.837 | 0.570 → 0.674 |

**四组里三组提升、一组持平，没有一组变差。**

> 单组提升只有 1~2 条查询，和 #48 那次失败的幅度相当——但那次是
> **符号不定**（两降两平），这次是**方向一致**（三升一平），
> 而且词法通道的提升更明显（最多 +0.104）。这是判定它真有效的依据。

### 词法通道为什么受益更多

因为词法命中天然更"脆"：它靠字面 token 对上，而一个片段被切在
句子中间时，另一半常常就在相邻片段里。向量通道对切分边界本来就不敏感
（语义相近的片段彼此也近），所以它的提升空间小。

### 与 #50 的关系

相邻片段**合并**（#50）和上下文扩展都在动相邻片段，但目的相反：

- 上下文扩展：**多带**一些上下文给同一个命中
- 相邻片段合并：把连续命中的多条**并成一条**，腾出结果位给别的文档

两者可以共存（合并之后再带上下文），但**必须先分别量化**——
否则出了问题分不清是谁造成的。

## 相邻片段合并（2026-09-12，#50）

### 做了什么

把**同一文档里序号连续**的命中合并成一条：

- 区间取并集、正文按原文顺序拼接并去掉重叠
- 分数取组里**最高**的那个，不做累加
- 新增配置 `CONTEXTDOCK_MERGE_ADJACENT`（**默认开**）

要解决的问题是「top-10 里三四条都是同一处内容，别的文档挤不进来」。
注意这个问题**光看 recall 看不出来**——它不关心结果是不是全来自同一篇，
所以这一节要同时看「覆盖的不同文档数」。

### 结果：四组切分参数，全部提升

| 切分 | recall | NDCG@10 | top-k 覆盖文档数 |
| --- | --- | --- | --- |
| 400/60 | 0.791 → 0.791 | 0.515 → **0.606** | 3.44 → **3.84** |
| 600/60 | 0.837 → 0.837 | 0.555 → **0.612** | 3.60 → **3.95** |
| 300/120 | 0.814 → **0.837** | 0.506 → **0.621** | 3.33 → **3.60** |
| 800/30 | 0.837 → **0.860** | 0.569 → **0.638** | 3.42 → **3.91** |

- **recall：两平两升，没有一组下降**
- **NDCG@10：全部提升，幅度 0.05~0.09**（本里程碑最大的一处提升）
- **top-k 覆盖的不同文档数：全部提升**

MRR 也从 0.462 升到 0.565。

> NDCG 提升这么多是合理的：合并把「同一处内容占三个名次」压成一个，
> 后面真正不同的结果就能往前排。它改的是**排序的构成**，不只是条数。

### 中间踩的一个坑，值得单独记

第一版实现为了给合并留出截断空间，把传给 `Hybrid.Search` 的 `topK`
从 10 改成了 30。结果 **recall 掉了 7 个百分点**（0.837 → 0.767）。

原因是 `Hybrid` 内部 `n = topK × mult`——**每路取回的候选数跟着变大了**，
而 RRF 的排名**依赖候选池大小**：候选一多，弱通道的噪声就压过强通道的
相关结果。这正是 #44 已经测出来的那件事，只是换了个地方又踩了一次。

证据很直接：同一个查询，改之前融合返回的第 3 名是 `design.md [2018,2299)`，
改之后整个 top-5 换成了另一批内容——那不是「少了几条冗余」，
是**排名本身变了**。

**修法**：把「每路取多少候选」和「融合结果截不截断」拆开，
新增 `Hybrid.SearchAll`——候选深度不变，只是不截断。
合并完再截断，腾出的位置由**同一份排名**里更深的名次填上。

> 这条已经写进 `Hybrid.SearchAll` 的注释和它的测试里。
> 教训是：**一个参数同时控制两件事时，改它一定会顺带改另一件。**

### 与上下文扩展（#49）的关系

两者都在动相邻片段，但目的相反：

- **上下文扩展**：多带一些上下文给同一个命中（输出变宽）
- **相邻片段合并**：把连续命中的多条并成一条（输出变窄）

它们**可以叠加**，而且方向互补。但按 #51 的要求，收益要**逐项量化**——
所以这一节和上一节是分开测的，没有混在一起跑。

### 默认值

`CONTEXTDOCK_MERGE_ADJACENT` 默认 **`true`**。依据就是上面那张表：
四组参数上 recall 无一下降、NDCG 与文档数全部提升。

## 四项质量改进的逐项量化（2026-09-12，#51）

四项改动（#47~#50）**逐项单独测**，不混在一起——否则出了问题分不清是谁造成的。

| # | 改进 | 结论 | 依据 |
| --- | --- | --- | --- |
| 47 | 代码块 / 表格感知切分 | **质量无变化**，保留（修的是结构缺陷） | recall 0.791 → 0.791 |
| 48 | 重叠起点吸附行边界 | **有害，已回退** | 8 组对比（2 方向 × 4 配置）无一更好 |

| 50 | 相邻片段合并 | **最有效** | NDCG@10 +0.091、文档数 +0.40，4 组全升 |

### #47 与 #48：两项「没有收益」

**都要如实记下来，而且性质不同**：

- **#47 是「测不出收益」**。它修的是一个确定存在的结构缺陷
  （围栏开标记被孤零零留在无关片段末尾），但那 43 条查询里
  没有一条的答案正好落在被切坏的碎片上。**留着，但不宣称它提升了什么。**
  将来评测集变大时要重新检验；如果证明只带来复杂度，就该回退。
- **#48 是「实测有害」**。而且不是单点数据——两种吸附方向、四组切分参数，
  8 组对比里不吸附一次都没输过。**回退，并把原因写进代码注释**，
  免得后人再"顺手修一下"。

### #49 与 #50：完全正交

> #49 是**输出侧**的（给同一条结果配更多上下文），

## 分数能不能判断相关性（2026-09-12，#52）

README 的「已知限制」里写着：问一个库里完全没有的问题，返回片段的 RRF 分约 `0.031`，
而真正命中时约 `0.033`——**几乎没差别**。这一节把那句印象换成了完整分布。

### 怎么测的

评测集新增一个子集 `norel`：**8 条语料里根本没有答案的查询**
（K8s 部署 Java、Python asyncio、MySQL 主从、React useEffect、Kafka 积压、
Nginx 反代、Excel 透视表、季度绩效面谈）。

它们的 `expect` 是空的——**期望的结果就是"没有结果"**。返回的每一条都按定义不相关。

> ⚠️ 关键是把「不相关」分成两种，性质完全不同：
>
> 1. **有答案但没命中**——分数高是正常的
> 2. **根本无答案**（norel）——它的一切都是噪声
>
> 阈值要挡的是第 2 种。混在一起看会把"查得到但没排好"误当成"查不到"。

### 结论一：RRF 分**完全不可分**

每条查询的**最高** RRF 分（阈值决策的单位是查询，不是单条结果）：

| 查询类别 | n | min | P50 | max |
| --- | --- | --- | --- | --- |
| 有答案 · 命中 | 34 | 0.0164 | 0.0325 | **0.0328** |
| 有答案 · 没命中 | 9 | 0.0164 | 0.0309 | **0.0328** |
| **无答案（norel）** | 8 | 0.0164 | 0.0306 | **0.0328** |

**三行的 min / P50 / max 几乎完全一样，无答案查询的最高分与有答案的完全相同（0.0328）。**

**没有任何阈值能把它们分开**——一个也没有。这直接验证了
[DESIGN §10](DESIGN.md) 那条警告，而且比原来的印象更强：不只是"差不多"，
是**分布本身重合**。

原因也很清楚：RRF 分是 `Σ 1/(k+rank)`，它只反映**名次**。
只要两个通道各凑出前十名，分数就落在同一个窄区间里——
而"凑出前十名"对任何查询都成立（见 README 的"没有相关性阈值"那条）。

### 结论二：原始余弦分**部分可分，但代价高到不可用**

| 查询类别 | n | min | P25 | P50 | max |
| --- | --- | --- | --- | --- | --- |
| 有答案 · 命中 | 34 | **0.5097** | 0.5856 | 0.6280 | 0.8681 |
| 有答案 · 没命中 | 9 | 0.5172 | 0.5358 | 0.5627 | 0.5880 |
| **无答案（norel）** | 8 | 0.4872 | 0.5177 | **0.5316** | **0.5604** |

无答案的最高余弦是 **0.5604**，而有答案的最低是 **0.5097**——
**两个区间重叠**。扫一遍阈值：

| 余弦阈值 | 判为无答案 | 其中真无答案 | 误杀有答案 | 漏放无答案 | 精确率 | 召回率 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.52 | 6 | 4 | 2 | 4 | 0.67 | 0.50 |
| 0.54 | 12 | 5 | 7 | 3 | 0.42 | 0.62 |
| 0.56 | 16 | 7 | 9 | 1 | 0.44 | 0.88 |
| **0.58** | 21 | **8** | **13** | **0** | **0.38** | **1.00** |
| 0.60 | 29 | 8 | 21 | 0 | 0.28 | 1.00 |

要让召回率到 100%（8 条无答案查询全识别出来），阈值就得降到 0.58——
而那时**43 条有答案的查询里有 13 条被误判成"没答案"**，精确率只有 0.38。

反过来，想要精确率好看（0.52 → 0.67），召回就只有一半。

> **两个方向都不好，而且这不是调参能解决的**：重叠区（0.51~0.58）里
> 同时住着"有答案但语义不强的查询"和"没答案但撞上了近似主题的查询"。
> 任何一条分界线都要在它们之间切开，而它们本来就没被数据分开。

### 该怎么做：不做阈值

issue #53 已经预见到这个可能：

> 如果 #52 的结论是「分数不可分」，那这个 issue 的正确做法可能是**不做阈值**，
> 转而把原始分暴露给 Agent 让它自己判断。

**数据支持这个结论。** 具体做法：

1. **RRF 分保持原样**——它是给排序用的，不该被当判别器
2. **把 `vector_score` / `lexical_score` 暴露到 MCP 输出**（现在没暴露），
   让 Agent 能拿到原始分
3. **不做自动过滤**——不因为分数低就把结果丢掉

为什么交给 Agent 比固定阈值好：Agent 能看到**内容**。
余弦 0.55 的那条如果是"讲的是同一类问题但细节不同"，Agent 一眼能判断；
而如果它真的不相关，Agent 也不会因为"工具说这是结果"就硬用。
固定阈值做不到这个区分——它只有那个数。

> ⚠️ 这套说法的代价也要说清：**它把判断责任推给了 Agent**。
> 如果 Agent 不加判断地照单全收，结果就是"永远返回 top-K"——
> 也就是现状。所以第 2 步（暴露原始分）是必需的，否则等于什么也没改。

## 相关性阈值：决定**不做**（2026-09-12，#53）

issue #53 的验收里写着：

> 阈值在评测集上的精确率 / 召回率都给出

### 问题

`hint` 只在**索引为空**时触发。库非空但问题完全不相关时，
检索照样返回 top-K 条，而且**不带任何信号**——Agent 无从知道

### 试了四类候选信号

| 信号 | 无答案（max） | 有答案（min） | 可分？ |
| --- | --- | --- | --- |

> 这比 #52 的结论更强：不只是"分数不可分"，
> 而是**没有任何可以从检索结果里算出来的量能分开这两种情况**。

### 所以交付的不是相关性判断

**不能做判断，就明说。** 有结果时随附一条说明：

结果按融合名次排序，但 score 不能用来判断相关性

这不是"给 Agent 一个不相关信号"——那种信号做不出来。它做的是
**把工具判断不了这件事本身告诉 Agent**：它能看到 `content`，
而工具只有分数。它缺的正是这条信息。

**假阳性为零**：这条说明不包含任何断言，所以不可能把真命中误判成不相关。
issue 里「假阳性比漏报更糟」那条约束由此满足。

### 顺带修掉一条长期 SKIP 的测试

`TestSearchGivesHintWhenEmpty` 原来的写法是：先导入一份无关文档、
再搜一个无关问题，期望"检索器召回不到"——于是它**永远 SKIP**，
因为库里非空时检索总会返回 top-K 条。

## 评测语料重置：这个动作已经不存在了（2026-09-12，#56）

### 前提不成立

issue 的假设是：

> 参数扫描要跑几十次，每次都涉及「清空 → 重新导入 → 切分 → 嵌入」。
> 手工做既慢又容易出错，还会因为残留数据让结果不可比。

**这一步在架构上已经没有了。** 评测器每次运行都从**空的内存存储**开始
（见 `eval.Run` 的说明），灌语料是每次运行的一部分。所以：

- 不存在"残留数据"——每次都是全新的库
- 不存在"手工清空"——它是自动的
- 不存在"忘记重置导致结果不可比"——那在结构上不可能发生

这不是"偷懒不做"，是**设计选择让这个工具失去了存在理由**：
用内存存储而不是 pgvector 做评测，顺带消掉了整个一类操作。

### 留下的是「状态可断言」这一半

另一半需求仍然成立：**得能确认"这批语料在当前参数下是什么状态"**。
没有它的话，评测数字变了时分不清是**检索质量变了**还是**切分/语料变了**——
而这两件事的处理方式完全相反。

交付 `go run ./cmd/eval -corpus`：

```text
语料状态（切分 400/60）：
语料                     片段数  sha256（前 12 位）
-----------------------  ------  ------------------
readme.md                    43        d93774a7e0fd
design.md                    22        56de45afbe65
pitfalls.md                  35        9c7371776362
rust-book-zh-testing.md      63        bd390be4e661
rust-book-zh-errors.md       40        054f6747418c
总计                        203
```

三个特点：

- **只切分、不嵌入**，所以不花任何 API 调用，也不碰存储
- **同时报指纹**：片段数变了有两种可能（参数变了 / 语料变了），
  只看片段数分不清，指纹能
- `-json` 输出同一个结构体，CI 可以直接断言（#57 要用）

### 顺带发现：`chunks_at_default` 早就过期了

写完这个工具一跑，它报 **203**，而 `corpus.json` 里记的是 **196**。

原因是 **#47 改了切分逻辑**，把围栏代码块和表格纳入保护，
片段数随之变化（pitfalls 33→35、rust-book 两份 60→63、38→40）。
而 `chunks_at_default` 是 #32 的时候打进去的，之后没人再动过它。

> 这正是"一个悄悄过期的数字比没有数字更糟"那句话的实例——
> 它不会报错，只是慢慢变得不对。

已经用 `-stamp` 重打。顺带修了 `-stamp` 的提示：内容没变、只有片段数变时
它原来会说「语料不可比」，而实际上**语料没动，动的是切分逻辑**——
这两件事的排查方向完全不同（一个查语料、一个查代码）。

## 检索质量门禁进 CI（2026-09-12，#57）

### 拦什么

CI 原来保证的是「代码能编译、测试能过」，**保证不了「检索质量没变差」**。
一个看起来无害的重构完全可能让 recall 掉 10 个点，而所有测试照样绿。

现在多了一条：

```bash
go run ./cmd/eval -validate
go run ./cmd/eval -fake-embed -quiet -gate eval/gate.json
```

### 关键决定：门禁跑的是**假嵌入**

CI 里没有 `SILICONFLOW_API_KEY`。三个理由让「用假嵌入」不只是权宜之计：

1. **不依赖密钥**：任何人 fork 下来都能跑，CI 也不用手动配 secret
2. **完全确定**：真实嵌入有微小抖动，每次数字都不同——而"门禁"需要
   「同一份代码 → 同一份数字」才能定阈值
3. **它足够抓住要抓的东西**（下面是实测）

**实测：把 RRF 的排序反转**（`sortAndTrim` 里的大于号改成小于号）：

| 指标 | 正常 | 排序改坏 | 下降 |
| --- | --- | --- | --- |
| 融合 recall@10 | 0.490 | **0.020** | 0.471 |
| 融合 NDCG@10 | 0.407 | **0.006** | 0.401 |
| 词法 recall@10 | 0.461 | 0.039 | 0.422 |
| 向量 recall@10 | 0.431 | 0.000 | 0.431 |

质量回归里最要命的那类（排序被改坏）它**完全接得住**。

> ⚠️ **代价要说清：假嵌入的向量没有语义**，所以它测不出"语义召回变差了"。
> 它能守的是「检索流程的排序行为没被改坏」。语义质量仍然要靠人跑真嵌入评测——
> 这也是为什么 `-fake-embed` 这个名字里带 `fake`：
> 让人一眼看出那个数字没有质量含义。

### 阈值：相对基线 + 固定容忍度，**不是**写死的绝对阈值

`eval/gate.json` 里存着一组基线指标，门禁比对后任何一项掉超过
`-tolerance`（默认 0.05）就退出非 0。

**为什么不用绝对阈值**（比如"recall 必须 ≥ 0.45"）：它只在评测集和语料
完全不变时才有意义。加一条查询、换一份语料、调一次切分参数，
那个数就得手调一次——而**"忘了调"的表现是门禁失效，不报错**。

相对基线让"下降"有明确含义：**与这次提交之前的自己比**。

容忍度写死 0.05 的依据：门禁跑的是假嵌入，数字完全确定，抖动只可能来自代码。
那种情况下 0.05 已经是很宽松的口子了（实测要拦的下降是 0.47）。

上界不设：**只报下降，不报上升**。上升可能是改进，值得更新基线，
但不该拦人——否则每次改进都要先改基线才能提交，而那会让人干脆把门禁关掉。

### 顺手补的一条：`-validate` 现在也核对片段数

`chunks_at_default` 是「这批语料在默认参数下切出多少个片段」的记录。
它很重要，但**特别容易悄悄过期**——改切分逻辑的人通常不会想到它。

`-validate` 现在会核对它，不符就报错并给出修复命令：

```text
语料片段数与清单不符：
  readme.md: 清单记 999，实际切出 43
  改过切分逻辑或参数？重打一次即可：
    go run ./cmd/eval -stamp
```

这条不是假设出来的需求：#56 做语料状态工具时就发现它已经过期了一轮
（#47 改了切分之后从 196 变成 203，过了很久才被发现）。

### CI 时长

门禁跑的是假嵌入，不联网，**实测 1~2 秒**（203 个片段 + 51 条查询，
全是内存计算）。增量可以忽略。

# 评测集格式

这份文档定义 ContextDock 检索评测集的**文件格式**，以及格式背后那条最关键的决策：
**期望命中锚定在原文引文上，不锚定在片段上**。

评测方法论（语料怎么选、指标怎么算、结论怎么读）见 [BENCHMARKS.md](BENCHMARKS.md)。

---

## 一、为什么锚定在原文引文上

最自然的写法是把期望命中写成「片段 ID」或「片段内容指纹」。两种都不行，原因同一条：

> **片段会变，而相关性不会。**

片段边界由切分参数决定。而这个里程碑里有好几件事都会动它：

| 要做的事 | 对片段的影响 |
| --- | --- |
| 切分参数扫描（MaxRunes × Overlap） | 片段边界**全变** |
| 代码块感知切分 | 一片变一片，或一片变两片 |
| 重叠起点吸附行边界 | 起点全挪 |
| 语料重置后重灌 | 数据库自增 ID 重排 |

绑在片段上的标识，一换参数就指不到原来那段文字了。而且**不会报错**——
评测器照样跑完，照样输出一份 report，只是里面对应那些条目的命中判据全成了噪声，
recall 掉一大截。看起来就像「改了参数之后检索变差了」，排查会从检索算法查起，方向全错。

所以锚点落在**与切分无关**的东西上：原文的一段引文。

引文还有一个附带好处——**可验证**。加载时必须在原文里唯一定位得到：

- 定位不到 → 标注抄错了，或者语料已经不是标注时那一版，两种情况都该立刻停下
- 定位到多处而没说是第几处 → 让标注者显式指定，不替他做选择

这两条都变成加载期的硬错误，而不是等到看报告时才发现数字不对。

### 命中判定

引文定位后得到原文里的一个 rune 区间 `[start, end)`。检索返回的片段也带
`StartOffset` / `EndOffset`，**同一套单位、同一份文本**。两者区间有重叠即算命中。

```text
原文 ────────────────────────────────────────────►
        ┌──────────┐            ← 片段 A
                 ┌──────────┐   ← 片段 B
             ●●●●●              ← 引文（期望命中）
             ▲      ▲
          A 与之重叠 → 命中

端点相接不算重叠：切分恰好把答案切成两半时，
相邻两段首尾相接是正常产物，算成两次命中会虚高。
```

> ⚠️ 单位必须是 **rune**。Go 的 string 索引是字节，一个汉字占 3 字节；
> 按字节算偏移，中文文档上会偏大近 3 倍，而代码照样编译、照样运行、
> 照样给出一个看起来合理的命中率。

## 二、目录结构

```text
eval/
├── corpus/                 # 语料快照（内容冻结在版本库里）
│   ├── readme.md
│   └── ...
├── corpus.json             # 语料清单：路径 + sha256 + 选取理由
└── queries/
    ├── zh.json             # 中文提问
    ├── en.json             # 英文提问
    ├── token.json          # 精确 token / 错误码
    ├── synonym.json        # 同义改写
    └── norel.json          # 语料里没有答案的查询
```

文件名必须与文件里的 `group` 一致。不一致会出现「统计进哪个组」和「文件叫什么」
两个真相，而这种错位只有对着报告逐条核对才看得出来。

## 三、评测集格式

```json
{
  "version": 1,
  "group": "zh",
  "title": "中文提问",
  "queries": [
    {
      "id": "zh-003",
      "query": "为什么不用中文分词库",
      "kind": "direct",
      "expect": [
        {
          "source": "design.md",
          "quote": "gojieba 依赖 cgo",
          "occurrence": 1,
          "grade": 2
        }
      ],
      "note": "DESIGN §3 的决策理由"
    }
  ]
}
```

### 顶层字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `version` | ✅ | 必须等于 `1`。不匹配直接报错——格式不兼容时宁可读不进来，也不要「尽力解析」 |
| `group` | ✅ | `zh` / `en` / `token` / `synonym` / `norel`，且必须与文件名一致 |
| `title` | ✅ | 展示用名称 |
| `queries` | ✅ | 至少一条 |

### query 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 人工标识（如 `zh-003`），全局唯一。失败分析时用它指代这一条 |
| `query` | ✅ | 喂给检索的原始查询串，全局唯一（跨文件查重） |
| `kind` | | `direct` / `indirect` / `multi-hop`。**省略则不参与分类统计** |
| `expect` | ✅ | 至少一条期望命中。**`norel` 组例外**——它按定义是空的，见下 |
| `note` | | 标注理由。复核时最难恢复的是「当时为什么判它相关」，没有 note 等于重标一遍没差别 |

`kind` 的三档对应三种完全不同的失败原因，是失败归因的第一刀：

- `direct` —— 用文档里的词问文档里的事
- `indirect` —— 换个概念问同一件事，**真正考验向量通道的那一类**
- `multi-hop` —— 答案散在多处，一条片段答不全；失败多半是切分把答案拆散了

### `norel`：语料里没有答案的查询

这一组和别的组**用途完全不同**：别的组量「找得准不准」，
它量「**找不到的时候，分数长什么样**」。

所以它的 `expect` 是**空的**——它期望的结果就是「没有结果」。
返回的每一条都按定义不相关，构成"纯噪声"的分数分布。

它是相关性阈值（#52 / #53）唯一的实验依据：没有一组"确定无答案"的对照，
就无法回答「分数能不能区分相关与不相关」。

> ⚠️ 校验器对别的组要求 `expect` 非空（为空会让那条查询在任何指标里
> 恒为未召回，悄悄拉低整体分数），**只对 `norel` 放行**。
>
> ⚠️ **它进了「总计」行，也就改变了总计的分母。**
>
> `norel` 是在 #44 之后加进来的。加之前总计是 **43 条**，加之后是 **51 条**——
> 而它按定义恒为 0 召回，所以同一个成绩在 51 条上会被摊薄
> （`0.667 × 51/43 = 0.791`，两个都对，但**不能直接比**）。
>
> 引用历史数字时务必连带说明分母，否则会看起来互相矛盾。见
> [BENCHMARKS.md](BENCHMARKS.md) 基线一节与
> [#67](https://github.com/XiaoleC05/ContextDock/issues/67)。

### expect 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `source` | ✅ | 语料清单里的**标识**（不是文件路径），让评测集与语料存放位置解耦 |
| `quote` | ✅ | 原文里的一段连续文本，必须在原文中能唯一定位 |
| `occurrence` | | 引文第几次出现，1-based。**省略时若引文不唯一则报错**，不静默取第一个 |
| `grade` | | `2` = 完全回答（缺省），`1` = 部分相关。怎么算分见 [BENCHMARKS.md](BENCHMARKS.md) |

> `occurrence` 省略与显式写 `1` 是**两种不同语义**：省略要检查引文唯一性，
> 写了 `1` 就是明确表示「我要第一次出现」。不区分的话，
> 一段出现两次的引文永远标不了第一次。

## 四、语料清单格式

```json
{
  "version": 1,
  "files": [
    {
      "source": "readme.md",
      "path": "eval/corpus/readme.md",
      "sha256": "……64 位小写十六进制……",
      "origin": "本仓库 README.md 的快照，取自 v1.0.0 发布后的 main",
      "why": "结构最杂：ASCII 架构图、表格、围栏代码块、中英混排",
      "chunks_at_default": 43
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `source` | 评测集引用它时用的标识 |
| `path` | 相对仓库根的文件路径 |
| `sha256` | 内容指纹，口径见下 |
| `origin` | 从哪来、什么版本。外部语料**必须**写清上游仓库、固定 commit 与许可 |
| `why` | 为什么选它：覆盖什么规模、什么语言、什么结构 |
| `chunks_at_default` | 在切分器默认参数（400 字 / 60 字重叠）下的片段数 |

`why` 不是装饰。语料选取是评测设计的一部分，不写下来，
后人只会看到一堆随机文件名，既不敢改也不知道缺什么。

`chunks_at_default` 用来回答「这批语料大概多大规模」，不必为此起一次完整检索。
⚠️ 它跟着切分参数走，**只由 `-stamp` 写入**，与指纹同批更新。手改必然过期，
而一个悄悄过期的数字比没有数字更糟。

> 评测**运行时**看到的片段数应以评测报告为准，不是这个值——报告里的才是当前参数下的实数。

### 指纹怎么算

1. 读文件字节
2. **把换行统一成 LF**（`\r\n` → `\n`，单独的 `\r` → `\n`）
3. 对结果算 sha256

第 2 步不能省。Windows 上 checkout 出来是 CRLF，CI 上是 LF；
不归一化的话同一份语料在两个平台上指纹不同，CI 必然报「语料漂移」——
而报出来的原因与真实原因（换行符）完全无关，排查从一开始就错了方向。

### 指纹不符时

**报错退出，不静默重跑，也不自动更新指纹。**

自动更新等于把这道防线取消掉：语料变了评测器默默认了，跑出来的数字与历史不可比，
而没有任何人知道。要更新的必须是人，且是一次显式动作：

```bash
go run ./cmd/eval -stamp
```

`-stamp` 重算全部语料的 sha256 **和片段数**，写回 `corpus.json`，并打印改了什么。

它和校验共用同一个 `Fingerprint` 实现——两处各写一遍的后果是：重打完指纹，
校验照样失败，而两边代码看起来都对。

⚠️ 指纹一改，**历史数字就不再可比**，必须重跑基线。

## 五、命令

```bash
go run ./cmd/eval -validate
```

只校验不跑检索。校验内容：

- 语料清单完整性 + **逐个文件核对 sha256**
- 每条 query 的必填字段、`kind` / `grade` 合法性
- `source` 是否在语料清单里
- **每个引文能否在原文里唯一定位**
- 全局的 query / id 查重
- 未知字段（手写 JSON 最常见的错误是 `quote` 拼成 `quotes`，
  标准解析器会静默忽略，那条期望命中就凭空消失了）

一次报出**全部**问题，不是遇到第一个就停——这个命令的用途是手工编辑时的即时反馈。

**校验通过时不输出任何东西，退出码 0。** 成功时的沉默让失败时的输出可以直接
被脚本和 CI 消费，不需要再写一层过滤器。

`-root` 指定仓库根（`eval/` 所在的目录），默认当前目录。

```bash
go run ./cmd/eval -stamp
```

重打语料指纹，**破坏性操作**，只在有意改过语料之后跑。见上一节。

```bash
go run ./cmd/eval -corpus        # 报告语料在当前参数下的确定状态
go run ./cmd/eval -corpus -json  # 同上，机读（CI 断言用）
```

**只切分、不嵌入**，所以不花 API 调用、也不碰存储。
同时报出每份语料的**片段数**与**指纹**——片段数变了有两种可能
（参数变了 / 语料变了），只看片段数分不清。

> ⚠️ 评测**不需要**「重置语料」这一步：每次运行都从空的内存存储开始，
> 灌语料是运行的一部分。见 [BENCHMARKS.md](BENCHMARKS.md) 的 #56 一节。

```bash
go run ./cmd/eval                    # 跑一次完整评测（默认参数）
go run ./cmd/eval -json -detail      # 机读 JSON + 逐条明细
go run ./cmd/eval -k 10 -mult 1      # 覆盖 RRF 参数
go run ./cmd/eval -maxrunes 200 -overlap 0   # 覆盖切分参数
```

**不需要数据库**：评测用内存存储。理由见 [BENCHMARKS.md](BENCHMARKS.md)——
简言之，检索路径目前是内存里的暴力扫描，换存储不改变任何检索结果。

结果分三路报出来：**只用词法 / 只用向量 / 融合**。「融合比单路好多少」
是这套评测最核心的输出——项目的整个设计都建立在那个假设上，
而只有把单路拿出来做同样的测量，假设才可检验。

## 嵌入缓存

`-cache`（默认 `.evalcache/`）把嵌入结果按**内容**缓存到磁盘：

- 切分参数一变，片段边界全变，但文字大范围重叠——按内容寻址能命中绝大部分
- 缓存让「几十种参数的扫描」从几小时降到几分钟
- 它**不是事实来源**：删掉只会变慢，不会改变任何数字
- 缓存键里带**模型名与维度**：换模型后绝不能读到旧向量

`.evalcache/` 已在 `.gitignore` 中。

## 六、改动评测集时

1. 编辑 `eval/queries/*.json`
2. 跑 `go run ./cmd/eval -validate`
3. 有错就改，直到**没有任何输出**
4. 改了语料内容的话，跑 `-stamp` 重打指纹，并**重跑基线**——
   指纹一变，历史数字就不再可比

> 标注流程、盲标原则、复核机制见下一节。

## 七、标注规范

标注质量直接决定评测结论的有效性，而标注是**人做的**，最容易引入无意识的偏见。
这一节把「怎么标」定下来，让别人能照着标出一份**可比**的评测集。

### 流程：顺序不能反

```text
1. 读一条查询，弄清它到底在问什么
        ↓
2. 在语料里人肉找能回答它的段落
        ↓
3. 记录：引文 + kind + grade + note
```

**第 2 步不许先跑一遍检索。**

这不是洁癖，是对抗一种自己察觉不到的偏见：先看到检索结果，人会把
「检索到的」**当成**「相关的」——每条结果看上去都挺合理，于是标注集就悄悄
变成了「检索结果的复制品」。那样评出来的分数会异常好看，而它衡量的只是
「系统和自己有多一致」。

同理，`note` 要写「这段为什么能回答这个问题」，不是「它排在第几」。

### 「零字面重叠」这个保证的边界

同义改写组靠一条自动化检查守住「只测向量通道」：查询与目标片段**零字面重叠**，
否则校验报错。但这条保证有一个前提，必须写下来：

> ⚠️ **它是相对默认分词方案（bigram）而言的。**
>
> 校验用的是项目自己的分词器。换成 unigram 之后，单字会撞上目标片段——
> 实测 unigram 下同义改写组能被词法通道命中 0.200，而这个数字来自
> 「比」「对」「的」这类常用字的噪声匹配，不是真的召回。见
> [BENCHMARKS.md](BENCHMARKS.md) 的分词方案对比。
>
> 也就是说：**这 10 条查询的「只测向量通道」性质，绑在 bigram 上。**
> 将来若换了分词方案，它们必须重新标注。

### 什么算「值得被检索到的一段」

| 判定 | 记不记 | grade |
| --- | --- | --- |
| 单独就能回答这条查询 | ✅ 记 | `2`（缺省） |
| 只回答了问题的一部分，或要与另一段合起来才完整 | ✅ 记 | `1` |
| 只是主题沾边，答不了问题 | ❌ **不记** | —— |

第三条是这套规范里最容易松掉的一条。**「讲的是同一件事」不等于「回答了这个问题」**——
一篇讲测试的文档里每段都和「怎么测」沾边，但只有讲了 `should_panic`
的那一段回答了「怎么验证函数会 panic」。松掉这一条，每个查询都会挂上七八个
expect，指标随之失去分辨力。

`kind: multi-hop` 的查询天然是一组 `grade: 1`——答案散在多处，每处都只答一半。

### 分级怎么算分

指标的定义在 [BENCHMARKS.md](BENCHMARKS.md)，这里只说**判定口径**：

- **recall@k**：`grade >= 1` 即算命中。部分相关算命中——它确实把用户往答案那边带了
- **NDCG@10**：增益按标准公式 `gain = 2^grade - 1`，即完全回答 3 分、部分相关 1 分
- **MRR**：第一条 `grade >= 1` 的结果，按其名次取倒数

> 为什么 recall 上不区分、NDCG 上区分：recall 回答的是「该带的有没有带上」，
> 那是个是非问题；NDCG 回答的是「排得好不好」，那里部分相关确实不如完全回答。

### 复核机制

两层：

1. **同批次内自检**：标完之后整体再扫一遍，专找「是否有多条指向同一段」
   「是否混进了仅主题相关的条目」——这两个错误占实际标注失误的大多数
2. **隔一段时间重标**：把 `note` 藏起来，只看查询重标一遍，比对一致率

第 2 层的价值在于**人会忘**。同一分钟内重标，你会记得上一次的答案，
一致率必然接近 100%，得不到任何信息。

### 已做的一次复核

本轮 43 条标注在完成后做过一次独立复核：由**另一次独立会话**（不同上下文、
看不到原始 `note`）在相同规则下重新标一遍，再逐条比对。

结果与局限记录在 [BENCHMARKS.md](BENCHMARKS.md) 的方法论章节。

> ⚠️ **没有做「隔天重标」。** 本里程碑在一个工作日内完成，无法真实等待一天。
> 这是这套评测目前的一个已知局限，不应被当作已经验证过的稳定性。
